# 要件定義書：文脈 — 選択式ドキュメント生成・資産化GUI

## 1. プロダクト概要

本アプリは、ユーザーがチャットで曖昧に要件を説明する代わりに、あらかじめ用意された選択肢・入力欄・追加パーツをGUI上で選びながら、SPEC.md、DESIGN.md、AGENTS.md、PROMPT、PROMPT for SKILL.md のいずれかのプロンプトを生成するWebアプリである。

単なるテキスト保存アプリではなく、**「選択を重ねることで要件・文脈・制約・出力形式を整理し、再利用可能なドキュメント資産として蓄積する」**ことを目的とする。

アプリ名は仮に **「文脈」** とする。

## 2. 解決したい課題

AIに依頼する際、多くのユーザーは「何を指定すればよいか」「どの順番で伝えればよいか」「どこまで制約を書くべきか」が曖昧なままチャット入力してしまう。その結果、AIからの出力品質が不安定になり、何度もやり取りを重ねる必要がある。

特に、要件定義、デザイン設計、エージェントルール、スキル作成用指示、汎用プロンプトでは、出力形式・目的・前提条件・制約・トーン・対象読者・禁止事項などを明確にする必要がある。しかし、毎回それを手書きするのは面倒であり、チームで品質を揃えることも難しい。

本アプリは、これらをGUI上の選択式UIに分解し、ユーザーが選択するだけで一定品質のMarkdown本文を組み立てられるようにする。

## 3. プロダクトの立ち位置

本アプリは、Claude、ChatGPT、Cursor、Codex、Claude Code、v0、LovableなどのAIツールそのものではない。

また、「完成済みテキストを並べてコピーするだけ」のツールでもない。

本アプリの立ち位置は、ユーザーの目的・制約・文脈・出力形式を整理し、Markdownプロンプトまたは汎用プロンプトを生成する **Structured Document Generator** である。

日本語で言えば、**構造化ドキュメント生成ツール** である。

## 4. 想定ユーザー

主な想定ユーザーは、AIを使って仕事を進める個人または小規模チームである。

具体的には、Webデザイナー、フロントエンドエンジニア、ディレクター、AI活用担当者、ライター、マーケター、業務改善担当者、個人開発者などを想定する。

ただし、初期MVPでは対象を広げすぎず、以下のような用途に絞る。

1つ目は、要件定義書そのものを作るための **SPEC.md生成**。
2つ目は、デザイン方針そのものを作るための **DESIGN.md生成**。
3つ目は、AIエージェントの常駐ルールを整理するための **AGENTS.md生成**。
4つ目は、汎用的なAI指示文を作るための **PROMPT生成**。
5つ目は、Codexなどで使うSKILL.mdを作成するための **PROMPT for SKILL.md生成**。

## 5. MVPで作る範囲

MVPでは、AI実行機能は必須にしない。

つまり、アプリ内でOpenAI APIやClaude APIを使って実際に文章生成することは、初期段階では必須ではない。まずは、GUIで選択した内容をもとに、高品質なMarkdown本文またはプロンプト本文を生成し、Markdown CopyまたはDownload Markdownを実行できる状態を目指す。

MVPで必要なのは、以下である。

| 項目        |  必須度 | 内容                                                       |
| --------- | ---: | -------------------------------------------------------- |
| 3カラムUI    |   必須 | サイドバー、メイン編集エリア、生成プロンプトエリア                                  |
| 出力形式選択    |   必須 | SPEC.md / DESIGN.md / AGENTS.md / PROMPT / PROMPT for SKILL.md |
| ヒアリング入力UI |   必須 | 出力形式、設問カード群、補助入力、制約、生成と確認                                      |
| パーツ追加    |   必須 | 出力形式と選択肢に応じてプロンプトパーツを追加                                     |
| パーツ編集    |   必須 | 登録済みパーツの本文を編集可能にする                                      |
| 生成プロンプト表示   |   必須 | 選択内容をリアルタイムまたはボタン操作で統合表示                                 |
| Markdown Copy |   必須 | 全出力形式で生成プロンプトをコピーできる。通常コピーとMarkdownコピーは同じ内容を扱う                                  |
| Download Markdown |   必須 | 全出力形式を.md形式でダウンロードできる                                             |
| テンプレート保存  |  準必須 | 選択状態をテンプレートとして保存                                         |
| ローカル保存    |   必須 | localStorageまたはIndexedDBで保存                              |
| DB連携      | 後回し可 | Supabase連携は第2段階でよい                                       |
| 認証        | 後回し可 | MVPでは不要                                                  |
| AI API実行  | 後回し可 | デモ段階では不要                                                 |

## 6. 非MVP範囲

以下は初期実装では行わない。

AIモデルの実行、複数ユーザーのチーム管理、課金機能、GitHub連携、Claude CodeやCodexとの直接連携、AIエージェント実行ログ管理、複雑なワークフロー管理、評価・スコアリング機能、生成本文A/Bテスト、LangfuseのようなLLMOps機能。

LLMOpsとは、Large Language Model Operationsの略で、大規模言語モデルを業務運用するためのログ管理・評価・監視・改善の仕組みを指す。本アプリは初期段階ではLLMOpsを目指さない。

## 7. 画面構成

本アプリは、基本的に3カラム構成とする。

左カラムはサイドバー。
中央カラムはヒアリング入力UI。
右カラムは生成されるプロンプトの表示エリア。

中央カラムと右カラムの間には、ドラッグで横幅を変更できることがわかる細いリサイズハンドルを配置する。

中央カラムと右カラムは、独立して縦スクロールできる。生成されるプロンプトが長くなっても、中央エリアの操作を邪魔しない。

## 8. サイドバー要件

サイドバーには以下を配置する。

上部にロゴを配置する。。

ナビゲーションは以下とする。

| セクション | 項目                    |
| ----- | --------------------- |
| メイン   | ダッシュボード               |
| ライブラリ | プロンプト一覧、テンプレート、パーツ   |
| 履歴    | 最近使ったもの、お気に入り         |
| 設定    | パーツを編集、タグ管理、チーム管理、設定 |

「パーツを編集」は設定セクションの最上部に配置する。

パーツとは、選択肢を選んだときに生成プロンプトへ追加される小さな文章パーツのことである。たとえば「推測で補完しない」「不明点は未確定と明記する」「判断基準を明記する」などがパーツである。

パーツは設問カードそのものではない。設問カードはユーザーから意図を引き出す入力UIであり、パーツは回答内容に応じてプロンプトへ挿入・反映される文章単位である。

## 9. メインエリア要件

メインエリアの上部にはページタイトルを表示する。

ページタイトルは **「新しいプロンプトを作成」** とする。

その右上には以下の操作ボタンを配置する。

| ボタン        | 内容                       |
| ---------- | ------------------------ |
| テンプレートから作成 | 保存済みテンプレートを呼び出す          |
| 保存         | 現在の選択状態を保存する             |
| Download Markdown | .mdファイルとしてダウンロードする |

メインエリアの中核は、多数の設問カードに回答しながらMarkdownプロンプトまたはプロンプト本文を組み立てるヒアリング入力UIとする。

基本構成は以下とする。

| 番号 | 領域        | 役割                                  |
| -: | --------- | ----------------------------------- |
|  1 | 出力形式      | 最終的に生成したいプロンプトを選ぶ                     |
|  2 | 回答量       | Quick / Standard / Deep など、回答する設問量を選ぶ |
|  3 | 設問カード群    | 出力形式ごとに異なる多数の質問に回答する                |
|  4 | 補助入力      | 選択肢だけでは表現できない固有情報や例外条件を書く            |
|  5 | 生成と確認     | 最終プロンプトの生成前に選択内容を確認する                   |

設問カード群は、出力形式ごとに20問以上になる可能性がある。各設問カードは、質問文、2〜5個以上の選択肢、必要に応じた自由入力欄を持つ。

設問量が多い場合は、画面内を章で分ける。章はタブ固定ではなく、2カラム配置、アコーディオン、ステッパー、進捗付きセクションなど、回答しやすい形式を採用する。

出力形式を選ぶと、表示する設問カード群を大きく切り替える。

SPEC.md、DESIGN.md、AGENTS.md、PROMPT、PROMPT for SKILL.md は、それぞれ目的も必要な情報も異なるため、同じ入力フォームを使い回さない。

## 10. 出力形式

出力形式では、ユーザーが生成したいプロンプトの用途を選ぶ。

項目はカード型UIとする。

各カードにはアイコン、英語ラベル、日本語説明を表示する。

英語ラベルは薄い色で表示し、日本語説明は英語より少し小さい文字サイズにする。

出力形式の選択肢は以下とする。

| 英語ラベル       | 日本語ラベル | 内容                           |
| ----------- | ------ | ---------------------------- |
| SPEC.md     | 要件定義   | アプリ、機能、Webサイト、業務改善などの要件定義を作る |
| DESIGN.md   | デザイン設計 | UI、ビジュアル、体験設計、デザイン方針を整理する    |
| AGENTS.md   | エージェントルール | AIエージェントの行動原則、禁止事項、プロジェクトルールを作る |
| PROMPT      | プロンプト  | 汎用的なAI指示文そのものを作る             |
| PROMPT for SKILL.md | スキル作成用プロンプト | SKILL.mdを作成するためのAI指示文を作る       |

## 11. 設問カード群

設問カード群では、選んだ出力形式に応じた専用項目を選択する。

このアプリでは、自由入力よりも選択式UIを中心にする。テキストエリアは、選択肢だけでは表現できない補足、固有名詞、例外条件を書くための補助入力として扱う。

前提情報に相当する項目は、必要な出力形式でのみ表示する。不要な場合は表示しない。

設問カード群の例は以下。

| 出力形式 | 主な選択項目の例 |
| ------ | ------------- |
| SPEC.md | プロダクト種別、対象範囲、ユーザー種別、機能粒度、非機能要件の有無、画面要件の有無、データ要件の有無、未確定事項の扱い |
| DESIGN.md | デザイン対象、トーン、レイアウト方針、カラー方針、タイポグラフィ方針、参考の扱い、レスポンシブ方針、禁止表現 |
| AGENTS.md | 適用範囲、行動原則、編集ルール、テスト方針、Git方針、セキュリティ方針、応答言語、禁止事項 |
| PROMPT | 使用先AI、タスク種別、役割、制約、出力形式、質問方針、粒度 |
| PROMPT for SKILL.md | 作成したいスキルの種類、発動条件、対象タスク、参照ファイル、使用ツール、プロンプト、失敗時の扱い |

各項目は、チェックボックス、ラジオボタン、セレクト、タグ選択、カード選択を基本とする。

固有の背景や素材を入れる必要がある場合のみ、短いテキスト入力またはテキストエリアを表示する。

すべての出力形式に、設問ごとの自由入力欄とは別に、プロンプト全体へ反映する自由入力欄を用意する。この欄は、プロジェクト固有の文脈、対象外にしたい条件、既存資料の要約、必ず含めたい要望などをまとめて入力するために使う。

全設問カードには、参考HTMLと同じ方向性で、選択肢に紐づかない自由入力欄を持たせる。ユーザーは各設問ごとに、選択肢では表現しきれないニュアンス、例外、固有名詞、補足条件を入力できる。

回答量は以下を基本とする。

| 回答量 | 設問数の目安 | 用途 |
| ------ | -----------: | ---- |
| Quick | 5〜8問 | 最小限の指示文を素早く作る |
| Standard | 12〜18問 | 実用的な粒度の指示文を作る |
| Deep | 20〜35問 | 制約、判断基準、出力構成まで細かく指定する |

## 12. 構成パーツ

構成パーツでは、生成されるプロンプトに含める要素を選ぶ。

ここがアプリの中核である。

ユーザーは、チェックボックス、カード、タグ、セレクトボックスを使って、必要なプロンプトパーツを追加する。

構成パーツも、出力形式によって候補を完全に切り替える。設問カード群で選択した内容に応じて、さらに候補を絞り込んでもよい。

初期パーツ例は以下。

| パーツ名      | 内容                  |
| ---------- | ------------------- |
| 背景・目的を追加   | 背景と目的のセクションを追加する      |
| 対象ユーザーを追加  | 誰向けのプロンプトかを明示する        |
| 制約条件を追加    | 守るべき条件を列挙する          |
| 不明点を明記     | 未確定事項を分けて記載する        |
| 優先順位を追加    | 重要度順に整理する            |
| プロンプトの構成を追加  | Markdownの見出し構造を指定する |
| チェックリストを追加 | 確認項目を追加する            |
| リスクを追加     | 想定リスクや注意点を追加する       |
| 次のアクションを追加 | プロンプトの末尾に次の行動を追加する     |
| 具体例を追加     | 抽象論だけでなく例を含める        |
| 判断基準を追加    | 良し悪しの基準を明確にする        |
| 代替案を追加     | 複数案の比較を追加する          |

構成パーツは、出力形式によって表示するパーツ候補が変わる。

たとえば SPEC.md の場合は、要件、非要件、ユーザー、画面、データ、権限、制約、未確定事項などのパーツを表示する。

DESIGN.md の場合は、トーン、レイアウト、カラー、タイポグラフィ、参考、禁止表現、UI状態、レスポンシブなどのパーツを表示する。

AGENTS.md の場合は、行動原則、編集制約、探索ルール、テスト方針、Git方針、セキュリティ、応答スタイル、禁止事項などのパーツを表示する。

PROMPT for SKILL.md の場合は、発動条件、入力、手順、参照ファイル、ツール利用、検証、プロンプト、例外処理などをAIに整理させるためのパーツを表示する。

## 13. 制約とトーン

制約とトーンでは、生成されるプロンプトの品質を安定させるための制約を指定する。

主な項目は以下。

| 項目     | 選択肢                           |
| ------ | ----------------------------- |
| 推測の扱い  | 推測しない / 推測するが明記 / 必要に応じて補完    |
| 不明点の扱い | 質問する / 未確定として分離 / 仮定を置いて進める   |
| 文体     | 簡潔 / 丁寧 / 実務的 / 技術者向け / 初心者向け |
| 出力密度   | 短く / 標準 / 詳細                  |
| 表形式    | 使わない / 必要に応じて使う / 積極的に使う      |
| 箇条書き   | 少なめ / 標準 / 多め                 |
| 専門用語   | そのまま使う / 簡単に説明する / 日本語訳を添える   |
| 禁止事項   | 選択式を基本とし、必要な場合だけ補足入力を許可する       |

このカテゴリでは、プロンプトの文体、粒度、未確定事項の扱い、禁止事項を定義する。

制約とトーンも全形式で完全共通にはしない。共通で使える基本項目を持ちつつ、出力形式ごとに表示項目を追加・削除する。

## 14. 生成と確認

生成と確認では、これまでの選択内容を確認し、最終プロンプトを生成する。

右カラムには常に生成プロンプトが表示されるため、このカテゴリは「最終確認」と「保存」の意味合いが強い。

表示内容は以下。

| 項目       | 内容              |
| -------- | --------------- |
| 選択した出力形式 | SPEC.mdなど       |
| 選択済み設問回答 | 設問カード群で選んだ専用項目 |
| 追加済みパーツ | 選択されたパーツ一覧     |
| 制約設定     | 推測の扱い、文体、出力密度など |
| 未入力の重要項目 | 空欄になっている重要項目    |
| 保存名      | テンプレートとして保存する名前 |
| 生成ボタン    | 右カラムのプロンプトを更新      |

## 15. クイック追加要件

メインエリア下部には「クイック追加」を配置する。

これは、よく使うプロンプト要素を素早く追加するためのエリアである。

例。

| ボタン        | 内容                |
| ---------- | ----------------- |
| 背景・目的を追加   | 背景説明を求めるパーツを追加   |
| 制約条件を追加    | 制約や禁止事項のパーツを追加   |
| 参考URLを追加   | 参考URLを含める欄を追加     |
| 出力例を追加     | 出力サンプルを指定する欄を追加   |
| チェックリストを追加 | 確認項目を出力させるパーツを追加 |


## 16. 右カラム：生成されるプロンプト

右カラムのタイトルは **「生成されるプロンプト」** とする。

右カラムには、現在の選択内容から生成されたプロンプト全文を表示する。

このエリアは縦スクロール可能にする。

生成されるプロンプトはMarkdown形式を基本とする。出力形式が PROMPT または PROMPT for SKILL.md の場合は、AIへ渡す指示文そのものを表示する。

右カラム下部には以下のボタンを配置する。

| ボタン          | 内容               |
| ------------ | ---------------- |
| Markdown Copy | 生成プロンプトをコピーする。通常コピーとMarkdownコピーは同じ内容を扱う |
| Download Markdown | .mdファイルとしてダウンロード |

## 17. リサイズハンドル要件

中央カラムと右カラムの間には、細い縦線または小さなグリップを配置する。

ユーザーがドラッグでメインエリアとプロンプトエリアの幅を変更できることが、さりげなくわかる見た目にする。

主張しすぎないが、ホバー時に少し色が変わる、またはカーソルが `col-resize` になるようにする。

MVPでは、実際のリサイズ機能を実装することが望ましいが、難しい場合でもUI上は実装予定として表現できる。ただし、ポートフォリオとして見せるなら実際に動く方がよい。

## 18. パーツ編集機能

パーツ編集は、本アプリの資産化機能の中心である。

ユーザーは、あらかじめ登録されているパーツの本文を編集できる。

パーツは以下の情報を持つ。

| フィールド  | 内容                               |
| ------ | -------------------------------- |
| パーツ名  | UI上に表示する名前                       |
| 説明     | 何のためのパーツか                       |
| 本文     | 実際にプロンプトへ挿入される文章                    |
| 対応出力形式 | SPEC.md / DESIGN.md / AGENTS.md / PROMPT / PROMPT for SKILL.md |
| カテゴリ   | 背景、制約、出力形式、確認、トーンなど              |
| タグ     | 検索・分類用                           |
| 有効/無効  | 表示するかどうか                         |
| 並び順    | UI上の表示順                          |

パーツ本文には変数を含められるようにする。

例。

```text
対象ユーザーは {{target_user}} です。
この前提を踏まえて、{{output_type}} に含める情報として整理する。
```

変数は、設問回答や補助入力で選ばれた値に置換される。

MVPで変数置換が難しい場合は、まずは単純な文字列結合でもよい。ただし、READMEでは将来的に変数対応する設計として説明する。

## 19. テンプレート機能

テンプレートとは、出力形式、設問回答の選択状態、選択済みパーツ、制約、トーンなどをまとめたプリセットである。

たとえば以下。

| テンプレート名      | 内容           |
| ------------ | ------------ |
| Webアプリ要件定義   | SPEC.md用     |
| LPデザイン設計     | DESIGN.md用   |
| プロジェクトエージェント設定 | AGENTS.md用   |
| 汎用AI指示文       | PROMPT用      |
| Codex作業スキル作成 | PROMPT for SKILL.md用    |

テンプレートを選ぶと、選択状態と初期パーツが自動で反映される。

MVPでは、初期テンプレートを数個だけ用意すればよい。

## 20. データ保存方式

MVPでは、データ保存はlocalStorageまたはIndexedDBでよい。

localStorageは簡単だが、大きなデータや構造化データには弱い。IndexedDBはブラウザ内データベースであり、プロンプト、パーツ、テンプレートのようなデータ管理に向いている。

ただし、実装難度を下げるなら、MVPはlocalStorageで十分である。

ポートフォリオとしてWebアプリ開発感を強めるなら、第2段階でSupabaseを導入する。

Supabaseを使う場合のテーブル候補は以下。

| テーブル            | 内容               |
| --------------- | ---------------- |
| document_projects | 作成中または保存済みのプロンプト |
| document_parts | パーツ本体           |
| templates       | テンプレート           |
| tags            | タグ               |
| project_parts  | プロンプトとパーツの紐付け     |
| export_history  | エクスポート履歴         |

## 22. プロンプト生成ロジック

生成プロンプトは、出力形式ごとの構成定義に沿って組み立てる。

プロンプト生成の基本構造は、design-creator-v2で使われているHTMLファイルの入力ロジックを参考にする。多数の設問カード、選択肢、設問ごとの補助入力、回答ログ、固定表示の生成操作を組み合わせ、回答内容を構造化データとして扱う。

画面デザインは参考画像の雰囲気を参考にする。ただし、実装時は要件定義書に書かれた出力形式、設問構造、全体自由入力欄、パーツ編集、プロンプト生成ロジックを優先する。

SPEC.md、DESIGN.md、AGENTS.md は、生成結果そのものがMarkdownファイル本文になる。

PROMPT と PROMPT for SKILL.md は例外として扱う。PROMPT は、任意の作業に使うAI指示文そのものになる。PROMPT for SKILL.md は、SKILL.mdを作成するためにAIへ渡す指示文そのものになる。

プロンプトは、以下の情報を使って組み立てる。

1. 出力形式ごとのセクション定義
2. 設問回答
3. 全体自由入力
4. 設問ごとの補助入力
5. 選択内容から追加されたパーツ
6. 手動で選択したパーツ
7. 制約
8. 不明点の扱い
9. 確認項目

SPEC.mdの場合の出力例は以下。

```md
# SPEC.md

## 1. 概要

- プロダクト種別: Webアプリ
- 対象範囲: MVP
- 目的: 選択式UIで構造化されたプロンプトを生成する

## 2. 背景

要件や制約を毎回手書きすると、指定漏れや粒度のばらつきが起きやすい。
本アプリでは、設問カードへの回答をもとに、再利用可能なMarkdownプロンプトを生成する。

## 3. 対象ユーザー

- Webデザイナー
- フロントエンドエンジニア
- ディレクター
- AI活用担当者

## 4. 機能要件

- 出力形式を選択できる
- 出力形式ごとに異なる設問カードを表示できる
- 回答内容からMarkdown本文を生成できる
- 生成されたMarkdownに対してMarkdown CopyまたはDownload Markdownを実行できる

## 5. 非機能要件

- 選択変更に対して右カラムを即座に更新する
- 作成中データをローカルに保存する
- 設問定義とパーツ定義をデータとして分離する

## 6. 未確定事項

- 出力形式ごとの設問数
- パーツ編集の初期実装範囲
- テンプレート保存の保存先
```

## 23. UIデザイン要件

全体は、モダンでミニマルな管理画面UIとする。

装飾は控えめにし、余白、細い境界線、軽いシャドウ、薄い背景色で構成する。

色は白・薄いグレー・黒に近いテキスト・アクセントカラー1色を基本とする。アクセントカラーは紫系を想定するが、強すぎないようにする。

カードやボタンの角丸はやや大きめにするが、ポップになりすぎない。

文字サイズは以下のように整理する。

| 用途        | サイズ感           |
| --------- | -------------- |
| ページタイトル   | 大きめ、太字         |
| カテゴリ名     | 中サイズ、やや太字      |
| カード英語ラベル  | 中サイズ、薄め        |
| カード日本語説明  | 小さめ            |
| 説明文       | 小さめ、薄いグレー      |
| 生成プロンプト本文 | 読みやすい等幅またはコード風 |

生成プロンプトエリアは、エディタやMarkdownプレビューのように見えるが、過度にコードエディタ風にはしない。

## 24. 操作フロー

基本操作フローは以下。

ユーザーは「新しいプロンプトを作成」を開く。
まず「出力形式」で SPEC.md や DESIGN.md などを選ぶ。
次に「回答量」で、回答する設問数の目安を選ぶ。
次に「設問カード群」で、その出力形式専用の多数の選択項目から必要なものを選ぶ。
次に「構成パーツ」で、選択内容に応じて提示された追加要素を選ぶ。
必要に応じて、補助入力で選択肢に収まらない固有情報や例外条件を書く。
右カラムには、選択内容を反映したプロンプトが表示される。
必要に応じて、生成プロンプトをMarkdown Copyでコピーするか、Download Markdownで.mdファイルとしてダウンロードする。
よく使う構成はテンプレートとして保存する。
既存パーツを改善したい場合は、サイドバーの「パーツを編集」から編集する。

ZustandはReact向けの軽量状態管理ライブラリである。複雑なグローバル状態を扱う場合に使いやすい。

MVPではReactのuseStateやuseReducerでも実装できるが、ポートフォリオとして状態設計を見せるならZustandを使う価値がある。

このプロジェクトはReact + Vite環境であるため、MVPはこのプロジェクト内に実装できる。サーバーサイド処理、ファイルシステムへの直接保存、認証、チーム共有、AI APIの安全な実行が必要になった段階で、APIサーバーや別アプリ化を検討する。

## 32. 完成判定

MVPの完成条件は以下。

ユーザーがデモURLを開き、SPEC.mdを選択し、SPEC.md専用の選択項目を選び、いくつかのパーツを選び、右カラムに生成されたSPEC.md本文を確認し、Markdown CopyまたはDownload Markdownを実行できること。

さらに、パーツ編集画面で既存パーツの本文を編集し、その変更が生成プロンプトに反映されること。

この2点ができていれば、MVPとして十分成立する。
